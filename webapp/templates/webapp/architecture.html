Key design decisions

  • Internal IDs, explicit mappings. Clients and locations have internal UUIDs; source_id_map records which QuickBooks customer (a sub-customer per location), Stripe customer and ad-platform location each corresponds to. Records of customers outside the registry, such as a sandbox's sample data, are counted as out of scope.
  • Two records of the same money. A Stripe payment is the processing record, a QBO payment the accounting record. They are matched, never added. Allocations (Line.LinkedTxn) decide which invoice is paid.
  • Matching order. Level 1: the Stripe PaymentIntent id the sync writes into the QBO memo; if several QBO records cite it, the one whose amount agrees is the match. Level 2: same client, currency and amount within ±{{ tol }} days, accepted only if mutually unique and nothing contradicts it (location, invoice reference). Otherwise NEEDS_REVIEW.
  • Time is a parameter. The {{ window }}-day sync window, aging and staleness use RECON_AS_OF ({{ as_of }}), never the clock.
  • Failures are data. Failed or partial pulls are recorded, retried with bounded backoff, never loaded over validated data, and shown as NO_DATA / INCOMPLETE / STALE, never $0.
  • Money is integer cents. QuickBooks decimals are parsed as Decimal and converted in one tested function; unknown currencies are rejected.
  • Independent ground truth. Expected statuses come from the scenario plan, keyed by a seed_key carried in Stripe metadata and the QBO memo. The evaluator can fail, and tests prove it does.
  • Web layer. Django renders every page from finrecon/dashboard_data.py, the same tested query module the static report uses. No ORM, sessions or logins: the app is read-only and connects with a read-only database role.

Limitations

  • Reconciliation data is synthetic (created in real QBO and Stripe sandboxes). The billing formula, fees and the Stripe→QBO sync are simulated to create known cases. Only the retail module uses real data, and it is kept separate.
  • Sandbox objects cannot be back-dated, so the business date is stored in Stripe metadata (event_date).
  • Single currency (USD) for reconciliation; multi-currency needs an explicit FX policy first.
  • QBO and Stripe are re-read in full each run (small volumes); the ad platform loads incrementally with a look-back.
